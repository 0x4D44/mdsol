# System Integration and Data Flow Analysis

**Date**: 2025.11.06  
**Codebase**: Solitaire (mdsol)  
**Analysis Level**: VERY THOROUGH

## Executive Summary

This document provides a comprehensive analysis of the solitaire game's system architecture, focusing on module integration, data flow patterns, UI-to-engine interaction, and critical system invariants. The application follows a single-threaded, event-driven Win32 architecture with clear separation between game logic (engine), solver logic, and UI presentation.

## 1. System Architecture Overview

### 1.1 Module Structure

The application consists of 4 main modules:

```
src/
├── main.rs       (~4300 lines) - Win32 UI layer, rendering, input handling
├── engine.rs     (~1034 lines) - Game state, move validation, scoring
├── solver.rs     (~655 lines)  - Solvability checker using DFS
└── constants.rs  (~56 lines)   - Shared resource IDs and constants
```

**Dependencies**:
- `main.rs` imports from: `engine`, `solver`, `constants`
- `engine.rs` imports from: `solver` (for solvability checks)
- `solver.rs` is self-contained
- `constants.rs` is leaf module (no dependencies)

### 1.2 Key Integration Points

1. **main.rs ↔ engine.rs**: UI layer owns `GameState`, calls public methods
2. **main.rs → solver.rs**: Direct import for hint generation logic (card color checks)
3. **engine.rs → solver.rs**: Calls `solve_deck()` for solvability testing
4. **constants.rs → main.rs**: Resource IDs coordinate with app.rc
5. **build.rs**: Compiles app.rc into binary at build time

fn is_valid_tableau_run(cards: &[Card]) -> bool {
    if cards.is_empty() { return false; }
    
    // All cards must be face-up
    for card in cards {
        if !card.face_up { return false; }
    }
    
    // Check alternating colors and descending ranks
    for window in cards.windows(2) {
        let upper = window[0];
        let lower = window[1];
        if upper.suit.color() == lower.suit.color() { return false; }
        if rank_value(upper.rank) != rank_value(lower.rank) + 1 { return false; }
    }
    true

**hit_test()** [line 2675]:
```rust
fn hit_test(state: &WindowState, x: i32, y: i32) -> HitTarget {
    let metrics = /* use cached or compute */;
    
    // 1. Check stock pile
    if point_in_rect(x, y, stock_x, top_y, card_w, card_h) {
        return HitTarget::Stock;
    }
    
    // 2. Check waste pile
    if point_in_rect(x, y, waste_x, top_y, card_w, card_h) && waste_count > 0 {
        return HitTarget::Waste;
    }
    
    // 3. Check foundations (4 piles)
    for foundation in 0..4 {
        if point_in_rect(x, y, fx, top_y, card_w, card_h) {
            return HitTarget::Foundation(foundation);
        }
    }
    
    // 4. Check tableaus (7 columns) - most complex
    for column in 0..7 {
        if x not in column bounds { continue; }
        
        let slots = &state.tableau_slots[column];
        
        // If cached slots match card count, use them
        if slots.len() == cards.len() {
            for (idx, slot) in slots.iter().enumerate().rev() {
                let height = if last_card { card_h } else { slot.height };
                if point_in_rect(x, y, col_x, slot.top, card_w, height) {
                    return Tableau { column, card_index: Some(idx) };
                }
            }
        } else {
            // Fallback: compute positions on-the-fly
            let mut y_pos = tableau_top;
            for (idx, card) in cards.iter().enumerate() {
                let offset = if card.face_up { face_up_offset } else { face_down_offset };
                if point_in_rect(x, y, col_x, y_pos, card_w, offset) {
                    return Tableau { column, card_index: Some(idx) };
                }
                y_pos += offset;
            }
        }
    }
    
    HitTarget::None
}
```

**Performance Optimization**: `tableau_slots` is populated during rendering (line 3517-3554) and cached for hit-testing. This avoids recomputing card positions on every mouse move.

**Algorithm**: Depth-first search with transposition table [line 432]:
```rust
fn dfs(
    start: State,
    tt: &mut HashMap<Key, bool>,  // Memoization table
    deadline: Instant,
    node_counter: &mut u64
) -> Option<bool> {
    // Iterative DFS using explicit stack to avoid stack overflow
    let mut stack = vec![Frame::new(start)];
    
    while let Some(frame) = stack.last_mut() {
        if !frame.initialized {
            frame.state.normalize();  // Auto-move cards to foundations
            
            if all_foundations_full() { return Some(true); }
            
            let key = hash_state(&frame.state);
            if let Some(&cached) = tt.get(&key) {
                return Some(cached);  // Memoization hit
            }
            
            frame.moves = generate_moves(&frame.state);
            frame.initialized = true;
        }
        
        if frame.next_child < frame.moves.len() {
            let mv = frame.moves[frame.next_child];
            frame.next_child += 1;
            
            let mut child = frame.state.clone();
            apply_move(&mut child, mv);
            stack.push(Frame::new(child));  // Explore child
        } else {
            // All children explored, backtrack
            tt.insert(frame.key, frame.found_success);
            stack.pop();
        }
        
        // Timeout check every 1024 nodes
        if (*node_counter & 0x3ff) == 0 && Instant::now() >= deadline {
            return None;  // Timeout
        }
    }
}
```

## 9. Critical Invariants

### 9.1 Game State Invariants

1. Sprite Index Consistency: Card sprite_index is immutable after creation
2. RNG Seed Immutability: Set once per deal for deterministic replay
3. Foundation Order: Ace to King of same suit only
4. Tableau Alternation: Alternating colors, descending ranks
5. Move Atomicity: All-or-nothing move operations
6. Score Non-Negativity: Standard mode uses saturating_sub()

### 9.2 UI Invariants

1. WindowState Ownership: One Box per window in GWLP_USERDATA
2. GDI Resource Cleanup: Reverse order cleanup on destroy
3. Capture Pairing: SetCapture paired with ReleaseCapture
4. Timer Lifecycle: Start/stop paired correctly
5. Layout Cache Validity: Cleared on resize/transient reset

### 9.3 Solver Invariants

1. Card Encoding: u8 in [0, 51], rank = c % 13, suit = c / 13
2. Normalization Idempotence: Multiple calls converge to same result
3. Timeout Granularity: Checked every 1024 nodes

## 10. Key Takeaways

### Architectural Strengths

1. Clean Separation: Engine independent of UI
2. Deterministic Replay: RNG seed enables replay
3. Robust Validation: All moves validated before application
4. Graceful Degradation: Falls back on missing resources
5. Comprehensive Undo: Full-state snapshots

### Integration Patterns

1. UI to Engine: One-way calls via public methods
2. Engine to Solver: One-way for solvability checks
3. Event-Driven: All logic triggered by Win32 messages
4. Single-Threaded: No concurrency concerns

### Critical Code Paths

Hot Paths (performance-sensitive):
- paint_window(): 16-60 FPS during animation
- hit_test(): Every mouse move
- WM_TIMER: 16ms-1000ms intervals

Cold Paths:
- deal_new_game(): Once per game
- Registry I/O: Startup/shutdown only
